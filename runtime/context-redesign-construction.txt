## 1. Core Philosophy: Compose Relationships into Expressions
Lain is a Lisp-like, propagator-based coordination language for describing high-level interactions between components.
Its central programming abstraction is the composition of transformations and relationships. Drawing on lambda calculus and functional composition, Lain allows programmers to construct, connect, and transform propagator networks through reusable abstractions.
Compose verbs into sentences. Do not concatenate nouns into names.
A Lain program should read like a meaningful expression describing how components relate, constrain, coordinate, and transform one another.
Think of a synthesizer, an electrical circuit, or a chemical reaction. The essential structure emerges from how components interact and what relationships their interactions maintain.
Cells provide the medium through which information propagates. They support the network’s operation, while the program’s primary expression concerns the relationships between its components.
This philosophy is related to Alan Kay’s emphasis on messaging and interaction in object-oriented programming. Lain extends this perspective through compositional network transformations and multidirectional information propagation.
Fundamental principles:
* Think in transformations, connections, constraints, and coordination.
* Express complex behavior by composing smaller relationships.
* Treat network topology as part of the program’s meaning.
* Preserve the distinction between a relationship and a particular procedure for evaluating it.
* Use cells and internal machinery when their semantics require them.
* Prefer reusable relational abstractions over specialized containers.
The ideal Lain program communicates what relationships hold, how they compose, and what information can propagate through them.

## 4. Declare Relationships, Not Execution Sequences
Lain networks describe concurrently existing relationships within activated topology. An unselected conditional body need not be expanded.
The textual order of network declarations should not be interpreted as an imperative execution sequence. Lexical scope, name binding, library loading, and explicit effect boundaries still matter; dataflow does not erase those constraints.
Consider:
```clojure
;; Schematic: f, g, and h must be defined by the application.
(define e
  (network [a b c]
    (-> (f a) b)
    (-> (g b) c)
    (-> (h c) a)
    (list a b c)))
```
These declarations describe network topology.
They do not imply that the first relationship must finish before the second begins.
Information propagates according to the dependencies and propagation semantics of the network.
Reason about topology
When reading or writing a network:
* Treat declarations as simultaneously existing relationships.
* Represent dependencies through connections.
* Allow propagation to follow available information.
* Avoid using source-code order to express control flow.
* Make ordering, buffering, and timing explicit when necessary.
* Consider feedback, convergence, and conflicting information.
A network is a persistent organization of relationships whose information state may evolve.
Anti-pattern: imperative thinking disguised as propagators
An agent may translate each step of a procedural algorithm into a separate propagator while retaining the original execution sequence.
This can produce syntactically valid Lain code with little benefit from the language’s relational capabilities.
Correction: Reconsider the problem as a network of constraints and interactions. Determine which dependencies are intrinsic to the domain and which were introduced by the procedural decomposition.

## language-introduction-cell
Lain is a connected dataflow language, not Clojure. Return raw parenthesized forms only; triple-backtick fences are invalid source. A callable is invoked as (f x); (-> x f) writes to the callable cell and does NOT call f. Only binding/argument vectors use literal brackets; construct data vectors with seq:empty and seq:append. Temporal sources accept occurrences from event:point, never bare message records or other behavior objects. A scan takes its source as its first argument; do not write events to the scan result. behavior:scan, map, and event-filter produce behavior objects, not ordinary records or vectors. Use behavior:latest-value to project a selected behavior value before passing to ordinary primitives. An optional fallback makes an empty behavior usable without inventing an occurrence. seq:project projects one key, so (seq:project :role xs) returns role strings, not message records. Model messages must be records with string :role and :content. System instructions must be first. The user ingress is a message RECORD, not a behavior or callable. You must capture its occurrences with event:point if you need a temporal source. (define name expression) binds a cell. (define pending) declares an unknown cell. (network [x y] expression) defines a callable. (let [x expression y expression] body) binds locals. (-> value target-cell) connects cells. (if condition yes no) selects a branch. Qualified names avoid editor collisions. Use data:record for immutable plain records, NOT struct, when passing data to primitives. (data:record :key value) constructs a record; (data:get :key record) reads it. seq:empty [] returns an empty vector; seq:append [vector element] appends one element; seq:concat [vector ...] concatenates vectors into one flat vector; for example (seq:concat (seq:append (seq:empty) 1) (seq:append (seq:empty) 2)) returns a vector containing 1 and 2; seq:last [vector] reads the last element. seq:project [key vector] projects a key over a vector. data:equal? [a b] compares values. event:point [id numeric-time value] captures a retained temporal occurrence. Each identity is immutable: later changes at its input do not withdraw earlier occurrences; connect its output to a behavior:source or scan. text:format [template & values] formats %s placeholders; for example (text:format "item %s" 7). Example individual operations: (define values (behavior:source)); (-> (event:point "sample" 1 7) values); (define sums (behavior:scan values + 0)). behavior:source [] creates a reducer cell; connect supported event:point results to it with ->. behavior:scan [source reducer initial] emits a state at EVERY ordered occurrence: each state is the corresponding accumulated prefix, not merely the final state. It uses a pure two-argument Lain callable; maps, filters, and reducers construct values and must not perform IO. Callback invocation uses a frozen temporary network, so callbacks must use their explicit arguments and immutable constants; reading changing external cells does not read the live network. behavior:event-filter [behavior predicate] keeps matching historical occurrences and their values. If a new occurrence is rejected, the last previously accepted occurrence remains available: latest-value of the filtered behavior stays unchanged. The predicate receives each behavior VALUE, which may itself be a vector or record. behavior:map [behavior callable] maps values. behavior:latest-value [behavior optional-fallback] projects its most recent value to an ordinary supported cell; before the first occurrence it returns the optional fallback, or remains unknown if no fallback was supplied. For example (behavior:latest-value values 0). Repeated identical events are suppressed; sources and scans are independent. model:request [record] submits { :id string :messages vector-of-role-content-records } to the existing model. Roles are strings system/user/assistant; content is a string. user-ingress publishes a record with :id, :time (odd integer), :role user, :content. Assistant time should be user time + 1 and assistant id must differ from user id. message-to-user [record] acknowledges a record containing :id :time :role assistant :content and returns that record with :acknowledged true. Its output, not generated source, is the delivered message. source:admit [complete-reply lexical-target support-cell-reference] admits complete forms sequentially, preserving earlier forms if a later one fails. environment:overview [environment optional-name-vector] lists visible binding titles, short headlines and references, including unknowns. The optional vector selects which bindings also include their full content; it does not recursively expand values. cell:reference [cell] yields an inspectable reference without waiting for its value. inspect:cell [reference] exposes only :edge, :value (strongest value), :inputs (producing connections), and :outputs (consuming connections). cell:value [reference] connects that edge's strongest value directly to an ordinary cell. cell:input [reference] returns a writable port for the referenced edge. Memory record fields contain references, so write through cell:input, not into a slot read projection. data:snapshot [compound] resolves a finite compound into a plain record; unknown slots remain pending. Use inspect:cell for edge/value/input/output inspection.

## reducer-verification-cell
Verified through compiled Lain, not a simulated conversation: a numeric source with occurrences 1@1 and 2@2, scanned with seq:append and an empty vector seed, emits prefix values [1] and [1,2]. Filtering those prefix values by whether their last number is greater than 1 keeps [1,2]. A later 0@3 is rejected by that predicate, leaving the filtered latest value [1,2]. The unfiltered scan advances to [1,2,0]. Exact replay produces no new values, and another source remains independent. Each call to behavior:source creates a new independent instance. A scan compiled into the lexical admission target also reduced an occurrence 5@1 with + and seed 0 to 5.
